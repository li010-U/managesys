## 一、项目完整建立过程

按"框架搭建 → 核心业务 → 安全加固 → AI 能力 → 稳定性与数据治理 → PostgreSQL 迁移与 CI 收尾"六阶段梳理。

### 阶段 0：框架搭建（2026-07-31）
**做了什么**
- 初始化仓库，搭建 FastAPI + SQLite 后端骨架与 Vue 3 + Vite 前端骨架。
- 确立分层：`backend/app/api`（路由）→ `services`（业务）→ `models`（模型）→ `schemas`（校验）→ `core`（配置/安全/限流）→ `db`（会话/兼容层）。
- 建立 `manage.py` 命令入口（init/backup/restore/export/import/check-data）。

**主要产出**
- 可运行的"机房/设备/机柜"基础 CRUD 框架，前端 Element Plus 布局与 3D 机柜初始视图。

**解决的问题**
- 为后续多模块并行开发提供了一个**分层清晰、可扩展**的基础架构。

### 阶段 1：核心业务开发（2026-08-03 → 2026-08-17）
**做了什么**
- 机柜/设备/机房资源管理、上架/下架，含机柜 U 位容量校验。
- 3D 机柜视图：SVG 角色/机柜渲染、2D 联动、导出当前视角图片（Three.js + ECharts）。
- 运维工单：附件上传、看板视图、负载均衡指派、分类审批流、自动化规则引擎。
- IP 资源：IP 地址注册表、自动分配、分配前防冲突、IP 变更历史、IP/VLAN 联动。
- 告警体系：告警生命周期（自动恢复/去重防抖/偶发识别）、机房资源统计。
- 业务系统管理、巡检（计划/任务/记录/问题）、知识库、角色权限（RBAC）。

**主要产出**
- 一套覆盖"机房资源 → 设备 → 网络 → 告警 → 工单 → 巡检 → 权限"的完整业务闭环。

**解决的问题**
- 把"资源台账 + 运维流程 + 监控告警"从零散需求整合成一个系统。

### 阶段 2：安全加固（2026-08-13 → 2026-08-19，多批）
**做了什么**

- 审计日志零信任重构：写入失败与业务请求隔离，不因审计故障拖垮业务。
- 初始管理员密码改为强随机生成；升级 Pillow 修复已知漏洞。
- SQL 注入面收敛：列表 LIMIT/OFFSET 参数化、动态 SQL 绑定参数（兼容 PG）。
- 统一错误语义：路由英文报错改中文；错误提示区分 5xx/超时/网络故障。

**主要产出**
- 全局安全中间件（CORS、TrustedHost、安全响应头）、统一异常处理、RBAC 权限点。

**解决的问题**
- 登录爆破、令牌失效不可控、注入面、错误信息误报（"网络错误"）。

### 阶段 3：AI 能力接入（2026-08-03 → 2026-08-19）
**做了什么**

**解决的问题**
- 从"玩具问答"到"会调用系统工具、能流式对话、能主动提醒"的真实智能助手。
- 反复出现的 AI"俄罗斯套娃式重复回复"与中文乱码回退问题。

### 阶段 4：稳定性与数据治理（2026-08-13 → 2026-08-21，持续）
**做了什么**
- 数据库事务统一提交点（get_db 单一提交）、巡检/工单 INSERT 后回读空值防护。
- 后台任务优雅取消（cancel + await）、SSE 流式收尾防挂死、AI 会话摘要并发上限。

**主要产出**
- 更稳的写入一致性、可预期的数据量上限、统一时区语义、无乱码的代码。

**解决的问题**
- 并发写超时、后台任务挂死、数据无限增长、时区混乱、编码乱码。

### 阶段 5：PostgreSQL 迁移与 CI 收尾（2026-08-21 + 持续）
**做了什么**
- 启用 Alembic 正式迁移并对齐历史 schema 差异；跨方言（SQLite/PostgreSQL）兼容改造。

- CI 完善：后端测试 + 启动冒烟 + openapi 校验、前端构建 + 单测、数据一致性门禁。
- **本机真实完成 SQLite→PostgreSQL 生产切换**：44 表、约 95 万行数据迁移，修复序列未前移、check-data 方言不兼容等真实 Bug；并做了日志轮转、重复索引清理、守护进程自治、每日自动备份。

**主要产出**
- 可承载多用户并发、可自动备份、可恢复、有 CI 把关的生产可运行形态。

**解决的问题**
- 生产从"单进程 SQLite、8 并发就大量 500"升级为"PG、高并发无 500、带自愈与备份"。

## 三、遇到并解决的问题（8–10 个典型）

> 每个问题按"问题描述 → 产生原因 → 解决思路 → 永久性预防"四要素展开。

### 问题 1：中文乱码 / 编码损坏（提交：af80f00、89e6020、af80f00）
- **问题描述**：大量源码的中文注释、用户可见文案（错误提示、审计文案、前端提示）显示为乱码（如 `鏁版嵁搴?/이터베스`），甚至出现损坏的字符数据。
- **产生原因**：文件用非 UTF-8 编码写入/在 GBK 控制台间复制，被错误转码后落盘；控制台输出用错误代码页读取 UTF-8 导致"看起来乱码"。
- **解决思路**：识别损坏源头 → 用 UTF-8 重新写入被编码破坏的中文串；恢复用户可见文案；清理存量脏数据（如带 ? 的审计记录）。
- **永久性预防**：全仓统一 UTF-8、`# -*- coding: utf-8 -*-` 头、编辑器保存 UTF-8；用 `rg`/`git blame` 定期扫描异常字符；用 Python `open(..., encoding='utf-8')` 读文件避免控制台干扰。

### 问题 2：SQLite 并发写超时 / 大量 500（aff3b1a）
- **问题描述**：多人同时操作时偶发 `database is locked` 与连接池 `QueuePool timed out`，最终 HTTP 500。
- **产生原因**：SQLite 同一时刻仅允许一个写者，高并发写竞争写锁；写锁等待的请求占满连接池后其余请求排队超时。
- **解决思路**：开启 WAL 模式 + `busy_timeout` + `synchronous=NORMAL`；连接池扩容并设 `pool_timeout` 快速失败；再叠加"进程内写锁串行化 + 带退避的有限重试"，把偶发写冲突降为可恢复。
- **永久性预防**：明确这是 SQLite 的固有天花板，稳妥方案是**演进到 PostgreSQL**；用压测脚本量化阈值，达到 TPS 上限即触发迁移决策点。

### 问题 3：5xx/超时/网络故障被误报成"网络错误"（4449f92）
- **问题描述**：后端 5xx 或请求超时，前端却提示"网络错误请检查连接"，误导排查。
- **产生原因**：前端错误拦截器把所有"无 response"的情况一律当网络错误，未区分状态码与超时。
- **解决思路**：按分支细化——有 response 按状态码（401/403/404/5xx/其余 4xx）给语义化中文；无 response 再区分 `ECONNABORTED`/timeout（提示超时）与真网络失败（提示检查连接）；被取消请求静默忽略。
- **永久性预防**：把这段分支抽成可测逻辑，并补前端单测（`index.spec.ts`）锁定文案，防止回归。

### 问题 4：SQL 注入风险 / 分页排序边界（fac8f68、1a1eb97）
- **问题描述**：列表查询的 LIMIT/OFFSET 与排序、动态条件存在字符串拼接注入面，且分页/排序边界不统一。
- **产生原因**：早期为方便用字符串拼接 SQL；不同接口自行实现导致排序字段、越界分页不一致。
- **解决思路**：将所有 LIMIT/OFFSET 改为绑定参数；把动态 SQL 改为参数化（并兼容 PG 的绑定风格）；统一读接口的分页/排序边界。
- **永久性预防**：约定"凡动态 SQL 一律绑定参数 + 只允许白名单排序键"；CI 数据一致性门禁 + 针对注入面的回归测试。

### 问题 5：3D 渲染残留 / 导出图空白（0d724c0、RACK3D_USAGE.md）
- **问题描述**：3D 机柜视图在 2D/3D 切换后残留旧渲染；导出当前视角图片出现空白。
- **产生原因**：2D 画布高度计算不足，3D 内容超出画布被裁掉；组件切换未正确清理渲染实例。
- **解决思路**：重算画布尺寸，让 2D 与 3D 两块都完整落在画布内；补充布局纯函数的 Vitest 回归测试。
- **永久性预防**：把"画布高度 / 3D 缩放"这类易错几何逻辑抽成纯函数并加测试，从源头锁定回归。

### 问题 6：时区混乱（8e15521）
- **问题描述**：时间戳含/不含时区混用，导致存储与展示相差 8 小时（naive/aware 比较还会引发 TypeError 500）。
- **产生原因**：系统时区与数据库默认时区不一致；部分时间用本地、部分用 UTC 混存。
- **解决思路**：统一为本地（北京时间）存储与展示；统一时间工具（now_local 等）；迁移存量 UTC 数据；修复 naive/aware 比较。
- **永久性预防**：收敛所有取时间的入口到一个工具模块；测试覆盖时区边界；配置明确 DB 时区（PG 用 Asia/Shanghai）。

### 问题 7：AI 助手"俄罗斯套娃式重复回复"+ SSE 挂死（6c4a4bd、d6d8472、e713d9a）
- **问题描述**：AI 回答出现滚雪球式重复、答不对题；SSE 流在异常时迟迟不结束，前端一直转圈。中文乱码时还输出英文。
- **产生原因**：模型在长历史+意图不明确时复读；历史回填导致自我重复放大；SSE 收尾路径未处理异常导致连接挂死；模型不理解中文时输出英文。
- **解决思路**：历史回填截断 + 惩罚项 + 复读早停与裁剪 + 更鲁棒 trim + 降低检测门槛；SSE 流式收尾防挂死（异常也终止）；模型输出英文时回退中文 mock。
- **永久性预防**：把"重复检测/裁剪/流式收尾/中文回退"固化为可测逻辑；给流式与非流式两条路径都加测试；SSE 增补超时护栏。

### 问题 8：审计日志拖垮业务 / 审计误记（9db3213、92ebf8e）
- **问题描述**：审计写入失败会导致业务请求 500；部分只读接口被错误地记录审计（引用未定义对象）引发异常。
- **产生原因**：审计与业务在同一事务、未做失败隔离；GET 只读接口误挂审计写入逻辑且引用错误变量。
- **解决思路**：审计日志零信任重构——写入独立、失败不影响业务主流程；移除只读接口的错误审计；补回归测试。
- **永久性预防**：约定审计为"旁路/尽力而为"，与业务事务解耦；只读接口默认不审计；用测试覆盖"审计失败业务仍成功"。

### 问题 9：登录 500 / 爆破误标 / 令牌失效不可控（11122f3、559010e、da23f17）
- **问题描述**：登录锁定时间戳 naive/aware 比较触发 TypeError 500；成功登录被误标为爆破；旧令牌无法在改密后失效。
- **产生原因**：时间比较时区类型不一致；爆破判定误用成功登录；JWT 无吊销手段只能等过期。
- **解决思路**：统一时间比较；爆破改为"同 IP 短时窗口连续失败"；JWT 引入 token_version，改密/注销即递增使旧令牌失效。
- **永久性预防**：把认证/锁定/吊销纳入回归测试；令牌结构（jti/type/ver）固化在安全模块并被测试覆盖。

### 问题 10：PG 方言不兼容 + 迁移后序列未前移（本次迁移真实踩坑）
- **问题描述**：迁移到 PostgreSQL 后（a）`check-data` 的 `HAVING c>1`（引用 SELECT 别名）在 PG 报 `column "c" does not exist`；（b）自增主键迁移后序列停在 1，新插入会主键冲突；（c）旧迁移 `DROP INDEX` 在 PG 因"唯一约束支撑索引"而失败。
- **产生原因**：SQLite 允许的方言写法（HAVING 引用别名、宽松类型）在 PG 上不合规；迁移脚本只建了表没推进序列；约束支撑索引不可随意 DROP。
- **解决思路**：`HAVING COUNT(*) > 1`（两者通用）；对每个自增表 `setval(seq, max(id)+1)` 并实测插入验证；DROP 改为幂等且 PG 分支仅建唯一索引。
- **永久性预防**：**用真实 PostgreSQL 跑迁移/体检/压测**（静态审查 + SQLite 测不出方言问题）；把"迁移后序列对齐、check-data 通过、行数一致"写入迁移验收清单。

## 四、技术替换与对比

本项目真实发生两次"换技术"：① SQLite→PostgreSQL；② AI 模型 provider 切换（DeepSeek/OpenAI/内网）。用表格对比并解释"为什么换、换的成本是什么"。

### 4.1 SQLite → PostgreSQL

| 维度 | SQLite（原） | PostgreSQL（现） |
|---|---|---|
| 性能（单条读） | 快，单文件零网络开销 | 稍慢但有连接池/预编译 |
| 并发写 | 单写者，8 并发即大量 500 | 多写者 MVCC，高并发无 500 |
| 连接/连接池 | 单文件，本质一个写锁 | 池化 `pool_size/max_overflow`，连接数受 `max_connections` 限制 |
| 维护成本 | 零安装、免运维 | 需装服务/数据目录/备份/防重启丢失 |
| 学习曲线 | 低 | 中（SQL 兼容但方言差异多） |
| 适用场景 | 单用户/轻量/本地原型 | 多用户在线、高写入、需要可靠性 |
| 替换代价 | —— | 数据迁移、方言修正、序列对齐、重启停机、备份策略重做 |

**为什么换**：压测明确量化出 SQLite 在 8 并发混合写时 47%~58% 请求 500（`database is locked`/`QueuePool timed out`），而 PostgreSQL 在 15 并发下 0×500（超额仅触发 503 容量护栏）。系统目标是"多人同时在线、长时间稳定"，SQLite 是明确的天花板。

**换的成本**：
- 数据迁移（44 表约 95 万行）——用项目自带 `migrate_sqlite_to_pg.py` 反射建表 + 批量拷贝，需停机保证一致性快照。
- 方言修正——`HAVING 引用别名`、`DROP 约束支撑索引` 等 SQLite 合法写法在 PG 不合法，逐一改为通用写法。
- 序列对齐——PG 显式插入 id 不会自动推进 identity 序列，需 `setval(seq, max+1)`，否则新插入主键冲突。
- 运行变更——PG 需可靠启动（建议注册服务）、每日自动备份（改用 `pg_dump -Fc`）、把 `pg_dump/psql` 加进 PATH 供定时任务使用。
- 收益：并发无 500、支持多 worker、有 MVCC 一致性、可备份/还原。

### 4.2 AI 模型 provider 切换（DeepSeek / OpenAI / 内网）

| 维度 | DeepSeek（默认） | OpenAI | 内网 (internal / coding paas) |
|---|---|---|---|
| 网络可达性 | 外网 | 外网 | 内网，无需出公网 |
| 成本 | 低 | 较高（按 token 计费偏贵） | 中（内网自建） |
| 中文效果 | 好 | 好 | 取决内网模型 |
| 部署合规 | 数据出内网 | 数据出内网 | 数据不出内网（合规优先） |
| 切换代价 | 低 | 低 | 低（统一 OpenAI 兼容接口） |

**为什么/如何换**：接入时统一走 OpenAI 兼容的 `/chat/completions` 协议，抽象成 `LLM_PROVIDER` + 各 provider 独立 `BASE_URL/API_KEY/MODEL` 配置，通过 `.env` 一个变量即可切换，无需改代码。
**换的成本**：很低——只要厂商兼容 OpenAI 接口，就只是改配置；真正的成本在"不是每款模型都稳定理解中文/不重复"，这属于模型行为差异，需靠上文第 7 项（重复检测/中文回退/流式护栏）来兜底。

> 三句话决策：**有没有多用户并发写 → 决定要不要 PG**；**数据能不能出内网 → 决定 AI provider**；**模型稳不稳定 → 决定要不要做护栏**。

## 核心结论与技术选型建议

1. **先选"会变重的正确底座"**：协同/多用户系统从一开始就应为 PostgreSQL 预留演进路径（Alembic 迁移、方言兼容层），而不是等到 500 频发再痛苦迁移。起手用 SQLite 快速验证可以，但要**早预算迁移成本**。
2. **性能问题要量化再决策**：别凭感觉"觉得能扛住"。本项目靠压测在 8 并发就测出 SQLite 崩塌，数据驱动了换 PG 的决定。
3. **SQL 方言是隐形雷区**：SQLite 合法写法在 PG 不一定合法（HAVING 别名、约束索引、宽松类型）。跨库项目必须**用真实目标库跑迁移/体检/压测**，静态审查 + SQLite 测不过出不来。
4. **把"易错逻辑"抽成纯函数 + 测试**：3D 画布、AI 重复裁剪、错误提示分支、时间换算——这些反复出问题的地方，抽函数并加回归测试，是性价比最高的"永久性预防"。
5. **AI 能力的关键不是模型，是护栏**：重复回复、SSE 挂死、乱码回退、工具授权——把 LLM 当"不可靠外部依赖"来兜底，比换更好的模型更优先。provider 用"OpenAI 兼容 + 配置切换"隔离，成本极低。
6. **生产稳定 = 自愈 + 备份 + 可回滚**：守护进程自动重启、每日 PG 备份（30 份保留）、一键迁移/回滚脚本、CI 门禁，这些"非功能"投入才是长跑系统不崩的根本。
